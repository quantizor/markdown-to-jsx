Security standards

Depth behind the security rules in AGENTS.md. This library's entire input surface is untrusted by definition: a markdown parser exists to render text somebody else wrote. Every parsing and rendering path is a user-input surface and gets screened accordingly.

Threat model

The output of this library is placed directly into a live DOM (JSX renderers) or into a document that will be (the html and markdown string compilers). An attacker controls the full markdown source, including any raw HTML embedded in it, and may also control link targets, image sources, and JSX prop values. They cannot control the options object, the override map, or the code around the call.

Consequences of that model:

- Sanitization is on by default and independent of any caller-supplied option. A caller who never reads the docs still gets a safe result.
- The string compilers (html, markdown) are held to the same bar as the JSX ones. Their output is more dangerous, not less, because it lands in a sink with no framework escaping underneath it.
- A defense that only holds for well-formed input is not a defense. Assume malformed encodings, truncated tags, and interleaved control characters.

URL sanitization

Blocked schemes are `javascript:`, `vbscript:`, and `data:` other than `data:image`. A browser reads a scheme only before a URL's first `/`, `?`, or `#`, so `https://example.com/?q=javascript:x` is safe, and a blocked name anywhere in that part is rejected (`feed:javascript:`, `notjavascript:`). The single regex is `/^[^/?#]*?(javascript|vbscript|data(?!:image)):/i`.

Markdown link and image destinations (inline and reference) are HTML-entity-decoded once at parse time before the sanitizer runs, matching CommonMark destination rules. That turns `&#106;avascript:` and `jav&#x61;script:` into a literal `javascript:` scheme the sanitizer rejects. Raw HTML URL attributes use the same entity-aware path in `isDangerousAttr`.

A browser decodes an attribute once more when it reads the string outputs, so the html output writes every `&` in a decoded destination as `&amp;`: `[x](&amp;amp;#106;avascript:)` stays the literal text `&amp;#106;avascript:`. Raw HTML attribute values are still encoded as written, so only they keep their entities. A footnote's text is never a destination: with a definition for `[^1]`, `[x][^1]` is `[x]` and a footnote reference.

Matching the literal scheme is not sufficient, and this is the mistake nearly every hand-rolled sanitizer makes. `java%73cript:alert(1)` and `%6a%61%76%61%73%63%72%69%70%74:...` both pass a literal test, and the browser executes them anyway because it decodes the attribute before acting on it. The working algorithm after entity decode:

1. Run the scheme regex on the raw input. Reject on a match.
2. If the input contains no `%`, tab, line feed, or carriage return it cannot be hiding a scheme, so return it unchanged. This is the fast path and it keeps the decode cost off the common case.
3. Otherwise cut the input at its first `/`, `?`, or `#`, `decodeURIComponent` what is left, strip everything outside `[A-Za-z0-9/:]` from the decoded string, and re-run the scheme regex on the stripped result. Stripping before the second test collapses interleaved tricks like `java\tscript:` and `java\nscript:` down to the bare scheme. The cut comes first since the strip removes `?` and `#`.
4. `decodeURIComponent` throws on a malformed sequence such as a lone `%`. Catch it and reject the URL rather than passing it through, wherever in the URL the sequence stands.

One decode pass is the right depth. Browsers decode a URL attribute once, so defending against one decode matches the threat; decoding until stable would over-reject legitimate URLs containing a literal `%xx` in their path.

The return type is `string | null`, where `null` means "unsafe, do not render". Callers drop the attribute entirely rather than emitting a broken or dangerous one. In JSX the prop becomes `undefined` and is omitted, never the attacker's string.

`data:image` is deliberately allowed because inline images are a legitimate low-risk use. `data:image/svg+xml` is the known soft spot: it passes the filter and can execute script when opened as a top-level navigation. That tradeoff is documented for consumers in the README and tracked in BACKLOG.md rather than silently narrowed, because blocking it would also block safe inline SVG.

Raw HTML attributes

Independent of the URL sanitizer, raw HTML attributes are screened as the parser builds element nodes:

- Any `on*` attribute with a string value is removed, case-insensitively. A bare boolean `on*` on a component-like tag (`<MyComponent onClick />`) is a prop set to true rather than an inline handler, so it is kept. Solid drops it from a native element, since Solid hands an `on*` prop to `addEventListener`, which throws on anything but a function.
- `srcdoc` on an iframe is removed.
- A name is judged as what it reaches in a renderer, ahead of the brace exemption below. Solid strips `attr:`, `prop:`, and `bool:` to reach the attribute or property named after them, so the rest of the name is what gets screened (`attr:onclick`, `prop:href`). `innerHTML` and `outerHTML` are removed since Solid and Vue put them into the page as markup; `dangerouslySetInnerHTML` and `ref` are removed since React, Solid, or Vue throw on a value markdown can supply, and `children` since React throws on an object child. `children` stays on a tag `overrides` registers, where it is a real prop, unless its value is a brace object or array, since no component can render that as a child. An override can still resolve the tag to a void element such as `img`, so the React and native element factories drop children on a void tag whenever overrides are in use.
- URL-bearing attributes (`href`, `src`, `action`, `formaction`, `poster`, `cite`, `background`, `data`, `longdesc`, `xlink:href`, and React's `xlinkHref`) are removed when the value resolves to a dangerous scheme, using the same decode-aware check above so entity-obfuscated schemes are caught.
- `attributeName` is removed when, after decoding and without its namespace prefix, it names a URL-bearing attribute or an `on*` attribute. A brace value counts as its bare name on a standard tag (`{href}`, which the JSX outputs resolve to `href`), and stays on a capitalized or hyphenated tag with the other brace values. SVG `animate` and `set` write `values`, `to`, `from`, and `by` onto the attribute it names, so `<a><set attributeName="href" to="javascript:…"/></a>` makes a live link while no value on the tag looks like a URL attribute. Removing the name leaves the animation with no target, whatever the values hold (`values` is a `;` list, so a scheme check on it would have to split).
- A JSX brace expression on a capitalized or hyphenated tag is a prop the renderer resolves, not a raw-HTML handler string, so it is kept. On a standard HTML tag it is screened like any other value. A brace `on*` value is the exception on a tag `overrides` does not register, unless `evalUnserializableExpressions` is on, since a browser runs `{...}` in a written attribute as a block statement. A hyphenated tag loses it everywhere, since React writes its string as an attribute. A capitalized tag loses it in every raw string and on a native element in Vue and Solid, and keeps it in the parsed `attrs`, since React drops it from a native element and a `createElement` or `renderRule` can make the tag a component. What a browser reads of what is left then decides that tag, so `<Foo onclick={a} x={ onclick={b} }>` is escaped. A URL-bearing attribute is outside the exemption unless its brace value is an object or array: `<Btn action={javascript:alert(1)}>` arrives as a string a component can write straight into a real `action`, so it gets the URL check above.
- A registered tag keeping its brace `on*` value is a deliberate 9.x compromise: removing it is a breaking change, so it stays until the next major. With `Foo` in `overrides`, `<Foo onclick={alert(1)}>` writes a live handler in the html and markdown outputs, on a native element in Vue, and in React on a hyphenated tag whose override leaves it a string, and throws in Solid, at render or on click.

What a browser reads, not what the parser reads

- Raw string outputs screen a tag the way the HTML tokenizer ends it: every `<` plus an ASCII letter starts a tag, a quote only opens a value right after `=`, and a tag still open at the end of the string counts as unfinished. An unsafe or unfinished tag is emitted with `&lt;` so it is visible text.
- Text in a comment, processing instruction, declaration, or CDATA section is not hidden from the screen. A browser ends a comment earlier than the parser can (`<!-->`), and treats the other three as bogus comments that end at the first `>`, so a tag after that point is live.
- Screening one quoted value reads each hidden tag up to `HIDDEN_TAG_READ_LIMIT` bytes past its `<`. Past the limit the tag counts as unsafe, which keeps the read linear on a long run of unclosed quotes.
- A rewritten string is read a second time, since removing an attribute can change what the next tag's quotes pair with. If the second read still changes it, every `<` is escaped.
- A code fence's info string goes through the same attribute screen, as it reaches the code element as attributes.
- A renderer can read the structure around code differently from the parser: where an HTML block ends, what a type 1 or CDATA block waits for, which fence closes, whether a backtick pairs before a tag, whether an `overrides` rename turns a line into a block. Any of these leaves a code body read as raw HTML or markdown, and no screen of the surrounding markup can rule them all out. So markdown output writes a code span or block as `<code>` or `<pre><code>`, with `&`, `<`, `[`, `]`, a backtick, `*`, `_`, `~`, `\`, and `|` as entities (a span also `:`, `.`, and `@`, since it stays inline markdown, where a bare URL or email address becomes a link), when its body or a fence's info string would be unsafe read that way. A filtered tag name counts only with `disableParsingRawHTML`: otherwise the document can write that tag raw and it passes through, so naming it in code adds nothing. A browser shows the same characters. Other code keeps its backticks or fence.
- An `overrides` rename can move where a renderer ends a block: `div` to `pre` ends at a type 1 closer on the line, `pre` to `div` at a blank line. Text the parser read as one raw string then splits, and a quote pairs with a later one. So markdown output with a rename parses what it wrote and writes that again with no overrides applied, the path any other source takes.
- A browser ends a processing instruction or CDATA section at its first `>`, marked at its terminator, which can sit inside a value of a tag the browser reads past that `>`. Marked then moves the value's closing quote to a new block, so it pairs with a later one. Markdown output writes a start tag past that `>` as text, wherever a raw string holds the markup, `<script>` bodies included.
- Marked copies a destination into `href` with its entities as written, so markdown output judges a numeric reference the way a browser reads it: no semicolon needed, any number of leading zeros.
- A renderer can read part of a destination as a link of its own: `[r]: </javascript:alert(1)[x](javascript:alert(1) "t")>` is one destination here, and written without its angle brackets it holds a live `[x](javascript:…)` to marked and micromark. So markdown output rejects a blocked scheme anywhere in a destination holding a character another renderer can split at (whitespace, `<`, `>`, a parenthesis, a bracket, a quote, a backtick, `&`, or `\`).
- `[^1]:` opening a block is a link reference to a renderer without footnotes, and a renderer can open a block where the AST has none (a line of a leading hard break reads as blank, a comment ends its line), so markdown output writes a colon right after a footnote reference as `\:` in every position. An ATX heading is one line, so a setext heading's line break is written as a space.
- Micromark strips a byte order mark at document start and marked keeps it as text, so only one reads the next characters as a block start. Markdown output writes one opening a text block as `&#xFEFF;`, since a parsed node can't tell whether it opens the document.
- Renderers restart block parsing inside raw HTML, at a blank line or after a first line they read as text, so an opener with no end on a later line (`<!--`, `<?`, `<![CDATA[`) stays raw through document end, and a browser reads a later block's text as written. Markdown output writes that opener with `&lt;`.
- A renderer also reads across nodes: a raw string ending in `](` or `]:` and the paragraph after it, one line down in a tight list item, form one link or reference definition. The destination is out of the raw screen's sight, so markdown output writes that `]` as an entity.
- A multiline `^` in JavaScript also matches after U+2028 and U+2029, so marked strips a `>` there when it reads a blockquote, and a tag ends somewhere else. Markdown output writes either character as an entity in a raw string when at most three spaces separate it from a `>`.
- A renderer without footnotes reads a footnote reference as text, and any renderer reads a reference definition as text when it joins a paragraph above it, so every written name and title stays inert as text: `<`, `[`, and `(` in a name and `<`, `[`, and `]` in a title are entities, the same in the reference and the definition.
- marked before 18 drops the backslash of `\[` and `\]` in link text and parses that text again, so `\[a\](javascript:…)` inside a link reads as a live link. Markdown output writes `](` in text as `\]\(`, and a `(` opening a text node as `\(`, since the node before it can end in `]` (`[^1](javascript:…)`).
- A tag hidden in a quoted value whose read ends past the tag holding it closes on a quote in text, which an output or a renderer writes as `&quot;`. A browser in a state that ends the value early then reads on to a quote in a later block, so that read counts as unsafe.
- Solid and Vue insert the screened source of a block holding `<pre>` as `innerHTML` as written. Their element helper compiles other HTML-shaped props, never that one: an element there reaches the page as `[object Object]`.
- Markdown output is read by another renderer, so a `<` before a letter in text is written `&lt;`, a quote in image alt text is written `&quot;` since marked 17 copies alt into a quoted attribute unescaped (18 escapes it), a `[`, `]`, or `\` in alt text is backslash-escaped since a bare `]` ends the image and turns the rest of the alt into markdown, a `![` in a raw string with a quote and then a `]` ahead of the next blank line is written `!&#91;` for the same marked reason, a comment's text gets the raw link screen since a renderer can read the comment as broken open, an autolink in a raw string ends only at a character up to U+0020, `<`, or `>`, as CommonMark reads it except that U+007F stays in the body since marked links it, so a Unicode space such as U+00A0 in the body of `<javascript:…>` does not hide the target from the screen, an autolink's body is read as text by a renderer that ends the autolink sooner and once the `<` is neutralized, so the walk resumes right after the `<` and a `]` in the body gets screened, and a second `<` ends the candidate there too, since neutralizing it would let the first close at a later `>`, a block sibling after raw HTML in a list item gets a blank line since an HTML block otherwise swallows the code fence that follows, a link or reference target with whitespace or an angle bracket is written percent-encoded, in angle brackets when a parenthesis has no partner, a link, image, or reference target unsafe once a renderer decodes it (`&amp;#106;avascript:`) is dropped, a footnote body holding raw HTML or an unsafe link goes through the parser rather than out as written, and an element's attribute string gets the same screen as its body.

Dangerous tag names (`script`, `iframe`, `style`, `title`, `textarea`, `xmp`, `noembed`, `noframes`, `plaintext`) are escaped separately by the `tagfilter` option, which defaults to on. Matching GFM, only each matching tag's leading `<` is replaced (`&lt;script>…&lt;/script>` in the HTML sink); the body and closer stay. JSX sinks emit the same inert source as text nodes (React also escapes `>` in text). Structured children of filtered parents still render normally so allowed nested tags stay live. In the html output the filter reads every raw byte, including inside a comment, processing instruction, declaration, CDATA section, or attribute value, since what a browser reads there depends on what earlier output left open (`<p><? a`, then a blank line, ends at the first `>` of the next block). A comment's text stays invisible and `&lt;` decodes back to `<` in a value, so only the source bytes change there. CDATA inside SVG or MathML does not decode, so a filtered name in it shows as `&lt;` text. Outside them a browser ends the same bytes at the first `>`, so what follows is live and the filter stays. The markdown output applies no tagfilter.

Evaluation is opt-in and stays opt-in

JSX prop expressions that cannot be serialized (functions, free variables) are kept as strings by default. `evalUnserializableExpressions` turns on `eval()` for them and must never become the default, never be enabled by another option as a side effect, and never be presented in documentation without the untrusted-input warning beside it.

Rules for changing any of this

- A change to a sanitization path ships with a test that fails without it. Include the encoded and interleaved variants, not just the literal one.
- Escape trusted internal constants too, not only user text. A font stack or class name interpolated raw into a quoted attribute closes the attribute at its first quote and silently drops everything after it. "This value is ours" is not a reason to skip escaping.
- Verify a fix across all six compilers. A hole patched in the React renderer while html still emits the raw bytes is not patched.
- Never widen an allowlist to make a test pass. If a legitimate input is being rejected, narrow the rule at its cause.
- `scripts/html-fuzz.ts` reads the html, markdown, and react outputs with a spec-conformant HTML tokenizer (parse5), reads the react, solid, and vue element trees prop by prop (markup never shows a prop a framework acts on), and must stay clean. Markdown output goes through both marked and micromark first, since renderers disagree on what is a link and a hole only one of them reads is still a hole. It also fails on a live tagfilter element in the html output, on an `attributeName` targeting a URL or `on*` attribute, and on the parser's lazy line marker reaching the AST. It allows two kept shapes: a `{...}` value on a capitalized tag, except a handler unless a sink registers the tag or React holds it as a prop, and a non-object value holding a dangerous URL in a URL attribute; and a bare handler name, which holds no script, except an unprefixed one on a Solid element, which throws.
