Security standards

Depth behind the security rules in AGENTS.md ("Inputs and error handling", "Security").

Threat model

The output of this library is placed directly into a live DOM (JSX renderers) or into a document that will be (the html and markdown string compilers). An attacker controls the full markdown source, including any raw HTML embedded in it, and may also control link targets, image sources, and JSX prop values. They cannot control the options object, the override map, or the code around the call.

Consequences of that model:

- The string compilers (html, markdown) are held to the same bar as the JSX ones. Their output is more dangerous, not less, because it lands in a sink with no framework escaping underneath it.
- A defense that only holds for well-formed input is not a defense. Assume malformed encodings, truncated tags, and interleaved control characters.

URL sanitization

Blocked schemes are `javascript:`, `vbscript:`, and `data:` other than `data:image`. A browser reads a scheme only before a URL's first `/`, `?`, or `#`, so `https://example.com/?q=javascript:x` is safe, and a blocked name anywhere in that part is rejected (`feed:javascript:`, `notjavascript:`). The single regex is `/^[^/?#]*?(javascript|vbscript|data(?!:image)):/i`.

Markdown link and image destinations (inline and reference) are HTML-entity-decoded once at parse time before the sanitizer runs, matching CommonMark destination rules. That turns `&#106;avascript:` and `jav&#x61;script:` into a literal `javascript:` scheme the sanitizer rejects. Raw HTML URL attributes use the same entity-aware path in `isDangerousAttr`. Every output but markdown sends an image source through the same sanitize-then-encode path as a link href, so a control character the sanitizer passed reaches the page percent-encoded (`![a](java&#1;script:x)` writes `src="java%01script:x"`); the encoded set is in specs/compilers.md, "Every compiler". The markdown output's destination rules are below.

A browser decodes an attribute once more when it reads the string outputs, so the html output writes every `&` in a decoded destination as `&amp;`: `[x](&amp;amp;#106;avascript:)` stays the literal text `&amp;#106;avascript:`. Raw HTML attribute values are still encoded as written, so only they keep their entities. A footnote's text is never a destination: with a definition for `[^1]`, `[x][^1]` is `[x]` and a footnote reference.

Matching the literal scheme is not sufficient, and this is the mistake nearly every hand-rolled sanitizer makes. `java%73cript:alert(1)` and `%6a%61%76%61%73%63%72%69%70%74:...` both pass a literal test, and the browser executes them anyway because it decodes the attribute before acting on it. The working algorithm after entity decode:

1. Run the scheme regex on the raw input. Reject on a match.
2. If the input contains no `%`, tab, line feed, or carriage return it cannot be hiding a scheme, so return it unchanged. This is the fast path and it keeps the decode cost off the common case.
3. Otherwise cut the input at its first `/`, `?`, or `#`, `decodeURIComponent` what is left, strip everything outside `[A-Za-z0-9/:]` from the decoded string, and re-run the scheme regex on the stripped result. Stripping before the second test collapses interleaved tricks like `java\tscript:` and `java\nscript:` down to the bare scheme. The cut comes first since the strip removes `?` and `#`.
4. `decodeURIComponent` throws on a malformed sequence such as a lone `%`. Catch it and reject the URL rather than passing it through, wherever in the URL the sequence stands.

One decode pass is the right depth. Browsers decode a URL attribute once, so defending against one decode matches the threat; decoding until stable would over-reject legitimate URLs containing a literal `%xx` in their path.

The return type is `string | null`, where `null` means "unsafe, do not render". Callers drop the attribute entirely rather than emitting a broken or dangerous one. In JSX the prop becomes `undefined` and is omitted, never the attacker's string.

`data:image` is deliberately allowed because inline images are a legitimate low-risk use. An SVG data URL is the exception outside an image: a browser runs the SVG's script when it opens one as a page (a link, a frame, an object), while an `<img>` never runs it. So `opensSvgAsPage` rejects `data:image/svg+xml` in every URL attribute but an image slot (`img src`/`srcset`, `source src`/`srcset`, `video poster`, `input src`, `image src`/`srcset`/`href`/`xlink:href`, since an HTML parser reads `<image>` as `<img>`), in the default sanitizer when it is given the tag and attribute, in the raw HTML screen whatever the `sanitizer` option, and in the markdown output's link destinations. It reads the media type before the first `,` with every character up to U+0020 removed, case-folded, and once more after percent-decoding (`svg%2Bxml`), so spacing, case, and an encoded `+` do not hide it. `sanitizer(url)` called with no tag keeps today's result, since it cannot tell an image from a link.

Raw HTML attributes

Independent of the URL sanitizer, raw HTML attributes are screened as the parser builds element nodes:

- Any `on*` attribute with a string value is removed, case-insensitively. A bare boolean `on*` on a component-like tag (`<MyComponent onClick />`) is a prop set to true rather than an inline handler, so it is kept (Solid drops it from a native element: specs/compilers.md, "solid").
- `srcdoc` is removed from every tag, a brace value included: an iframe runs it as a document, and a capitalized tag can reach an iframe through an override or a component that spreads its props.
- `style` is removed when `isUnsafeStyle` finds a `javascript:`, `vbscript:`, or non-image `data:` URL as a CSS function argument (`url(`, `image-set(`, after a `(` or `,`), or a legacy script hook (`expression(`, `-moz-binding`, a `behavior` property). The value is read as a browser reads it first: entities decoded, `/* */` comments removed, CSS escapes decoded (`\6a` is `j`), every character up to U+0020 and every quote dropped, case folded. So `url(/**/javascript:x)`, `url(\6a avascript:x)`, and `expr/**/ession(x)` match. The JSX outputs, which turn the value into a style object, run the same check per declaration.
- A name is judged as what it reaches in a renderer, ahead of the brace exemption below. Solid strips `attr:`, `prop:`, and `bool:` to reach the attribute or property named after them, so the rest of the name is what gets screened (`attr:onclick`, `prop:href`). `innerHTML` and `outerHTML` are removed since Solid and Vue put them into the page as markup; `dangerouslySetInnerHTML` and `ref` are removed since React, Solid, or Vue throw on a value markdown can supply, and `children` since React throws on an object child. `children` stays on a tag `overrides` registers, where it is a real prop, unless its value is a brace object or array, since no component can render that as a child. An override can still resolve the tag to a void element such as `img`, so the React and native element factories drop children on a void tag whenever overrides are in use.
- URL-bearing attributes (`href`, `src`, `action`, `formaction`, `poster`, `cite`, `background`, `data`, `longdesc`, `xlink:href`, and React's `xlinkHref`) are removed when the value resolves to a dangerous scheme, using the same decode-aware check above so entity-obfuscated schemes are caught.
- `content` gets that check when its decoded value, after leading ASCII whitespace, opens with a digit or `.` (a `<meta>` refresh delay). The check strips the delay, an optional `url=`, and an opening quote before reading the URL, so `0;url=javascript:…`, `0;javascript:…`, and an SVG data URL (`0; URL='data:image/svg+xml,…'`) lose the attribute and `0;url=https://x.y` keeps it. Attribute screening has no tag context, so a `content` value on any tag that opens with a digit and names a blocked scheme loses the attribute too (`content="5 javascript:x"`).
- `attributeName` is removed when, after decoding and without its namespace prefix, it names a URL-bearing attribute or an `on*` attribute. A brace value counts as its bare name on every tag (`{href}`, which the JSX outputs resolve to `href`), so a capitalized or hyphenated tag keeps it only when it names neither kind of attribute or is an object or an array that is not valid JSON. SVG `animate` and `set` write `values`, `to`, `from`, and `by` onto the attribute it names, so `<a><set attributeName="href" to="javascript:…"/></a>` makes a live link while no value on the tag looks like a URL attribute. Removing the name leaves the animation with no target, whatever the values hold (`values` is a `;` list, so a scheme check on it would have to split).
- A JSX brace expression on a capitalized or hyphenated tag is a prop the renderer resolves, not a raw-HTML handler string, so it is kept. On a standard HTML tag it is screened like any other value. A brace `on*` value is the exception, since a browser runs `{...}` in a written attribute as a block statement: a tag `overrides` does not register loses it unless `evalUnserializableExpressions` is on, and a registered tag loses it from every raw string (the html and markdown outputs). A registered hyphenated tag keeps it only in the parsed `attrs`, for `renderRule`. A registered capitalized tag keeps it in the parsed `attrs` and in the source the JSX renderers re-parse (`_rawAttrsKeepingProps`, the same span list that keeps `children`), and `withoutHandlerSource` passes it on only when the renderer's own tag lookup resolves to a component: React, Solid, and React Native give the component the string as a prop, an override that renders an element (`'a'`, `{ component: 'a' }`, `{ props: {} }`) loses it, and Vue drops it from a component too, since Vue writes an undeclared prop onto the component's root element. What a browser reads of what is left then decides that tag, so `<Foo onclick={a} x={ onclick={b} }>` is escaped. `srcdoc` is outside the exemption, and a URL-bearing attribute or `attributeName` is too unless its brace value is an object or an array that is not valid JSON: `<Btn action={javascript:alert(1)}>` arrives as a string a component can write straight into a real `action`, so it gets the URL check above. A brace array is screened as the string a renderer writes for it, its items joined with commas, since every JSX output turns an array attribute into that string (`attributeName={["href"]}` reaches the page as `href`).

What a browser reads, not what the parser reads

- Raw string outputs screen a tag the way the HTML tokenizer ends it: every `<` plus an ASCII letter starts a tag, a quote only opens a value right after `=`, and a tag still open at the end of the string counts as unfinished. An unsafe or unfinished tag is emitted with `&lt;` so it is visible text.
- Text in a comment, processing instruction, declaration, or CDATA section is not hidden from the screen. A browser ends a comment earlier than the parser can (`<!-->`), and treats the other three as bogus comments that end at the first `>`, so a tag after that point is live.
- Screening one quoted value reads each hidden tag up to `HIDDEN_TAG_READ_LIMIT` bytes past its `<`. Past the limit the tag counts as unsafe, which keeps the read linear on a long run of unclosed quotes.
- A rewritten string is read a second time, since removing an attribute can change what the next tag's quotes pair with. If the second read still changes it, every `<` is escaped.
- A code fence's info string goes through the same attribute screen and the same attribute processing as a raw `<code>` tag (a `style` object, `href` and `src` through the caller's `sanitizer`), as it reaches the code element as attributes.
- A renderer can read the structure around code differently from the parser: where an HTML block ends, what a type 1 or CDATA block waits for, which fence closes, whether a backtick pairs before a tag, whether an `overrides` rename turns a line into a block. Any of these leaves a code body read as raw HTML or markdown, and no screen of the surrounding markup can rule them all out. So markdown output writes code whose body or fence info string would be unsafe read that way as `<code>` or `<pre><code>` with entities, which a browser shows as the same characters (form and the `disableParsingRawHTML` case: specs/compilers.md, "Code").
- An `overrides` rename can move where a renderer ends a block: `div` to `pre` ends at a type 1 closer on the line, `pre` to `div` at a blank line. Text the parser read as one raw string then splits, and a quote pairs with a later one. So markdown output with a rename writes twice, the second time with no overrides applied, the path any other source takes (specs/compilers.md, "Document").
- A browser ends a processing instruction or CDATA section at its first `>`, marked at its terminator, which can sit inside a value of a tag the browser reads past that `>`. Marked then moves the value's closing quote to a new block, so it pairs with a later one. Markdown output screens a start tag past that `>` wherever a raw string holds the markup, `<script>` bodies included (`screenMarkupBody`, specs/compilers.md, "Raw HTML").
- Marked copies a destination into `href` with its entities as written, so markdown output judges a numeric reference the way a browser reads it: no semicolon needed, any number of leading zeros.
- A renderer can read part of a destination as a link of its own: `[r]: </javascript:alert(1)[x](javascript:alert(1) "t")>` is one destination here, and written without its angle brackets it holds a live `[x](javascript:…)` to marked and micromark. So markdown output rejects a blocked scheme anywhere in a destination holding a character another renderer can split at (whitespace, `<`, `>`, a parenthesis, a bracket, a quote, a backtick, `&`, or `\`).
- `[^1]:` opening a block is a link reference to a renderer without footnotes, and a renderer can open a block where the AST has none (a line of a leading hard break reads as blank, a comment ends its line), so markdown output escapes a colon right after a footnote reference in every position, and writes a setext heading's line break as a space, since an ATX heading is one line (specs/compilers.md, "Text", "Headings").
- Micromark strips a byte order mark at document start and marked keeps it as text, so only one reads the next characters as a block start. Markdown output entity-encodes one opening a text block (specs/compilers.md, "Text"), since a parsed node can't tell whether it opens the document.
- Renderers restart block parsing inside raw HTML, at a blank line or after a first line they read as text, so an opener with no end on a later line (`<!--`, `<?`, `<![CDATA[`) stays raw through document end, and a browser reads a later block's text as written. Markdown output neutralizes that opener (`screenUnendedOpeners`).
- A renderer also reads across nodes: a raw string ending in `](` or `]:` and the paragraph after it, one line down in a tight list item, form one link or reference definition. The destination is out of the raw screen's sight, so markdown output neutralizes that `]` (`screenRawLinks`).
- A multiline `^` in JavaScript also matches after U+2028 and U+2029, so marked strips a `>` there when it reads a blockquote, and a tag ends somewhere else. Markdown output screens either character in a raw string (`screenLineSeparators`).
- A renderer without footnotes reads a footnote reference as text, and any renderer reads a reference definition as text when it joins a paragraph above it, so markdown output writes every name and title inert as text (specs/compilers.md, "Links, images, references").
- marked before 18 drops the backslash of `\[` and `\]` in link text and parses that text again, so `\[a\](javascript:…)` inside a link reads as a live link. Markdown output escapes `](` in text, and a `(` opening a text node, since the node before it can end in `]` (`[^1](javascript:…)`; forms: specs/compilers.md, "Text").
- A tag hidden in a quoted value whose read ends past the tag holding it closes on a quote in text, which an output or a renderer writes as `&quot;`. A browser in a state that ends the value early then reads on to a quote in a later block, so that read counts as unsafe.
- marked 17 copies image alt into a quoted attribute unescaped (18 escapes it), so markdown output encodes a quote in alt text.
- A bare `]` ends an image and turns the rest of its alt into markdown, so markdown output escapes `[`, `]`, and `\` in alt text, and screens a `![` in a raw string that a quote and then a `]` follow before the next blank line.
- A renderer can read a comment as broken open, so a comment's text gets the raw link screen.
- marked links an autolink holding U+007F, so in a raw string an autolink ends only where CommonMark ends it except that U+007F stays in the body, and a Unicode space such as U+00A0 in the body of `<javascript:…>` does not hide the target from the screen.
- A renderer that ends an autolink sooner, or meets it once its `<` is neutralized, reads the body as text, so the walk resumes right after the `<` and a `]` in the body gets screened. A second `<` ends the candidate, since neutralizing it would let the first close at a later `>`.
- An HTML block swallows a code fence that follows it in a list item, so a block sibling after raw HTML gets a blank line.
- A renderer reads whitespace, a control character, or an angle bracket in a target as its end, and decodes entities in it (`&amp;#106;avascript:`), so markdown output encodes the first and drops a target unsafe once decoded (specs/compilers.md, "Links, images, references").
- A footnote body holding raw HTML or an unsafe link goes through the parser rather than out as written, and an element's attribute string gets the same screen as its body.

Dangerous tag names (`script`, `iframe`, `style`, `title`, `textarea`, `xmp`, `noembed`, `noframes`, `plaintext`) are escaped separately by the `tagfilter` option, which defaults to on. Matching GFM, only each matching tag's leading `<` is replaced (`&lt;script>…&lt;/script>` in the HTML sink); the body and closer stay. JSX sinks emit the same inert source as text nodes (React also escapes `>` in text). Structured children of filtered parents still render normally so allowed nested tags stay live. In the html output the filter reads every raw byte, including inside a comment, processing instruction, declaration, CDATA section, or attribute value, since what a browser reads there depends on what earlier output left open (`<p><? a`, then a blank line, ends at the first `>` of the next block). A comment's text stays invisible and `&lt;` decodes back to `<` in a value, so only the source bytes change there. CDATA inside SVG or MathML does not decode, so a filtered name in it shows as `&lt;` text. Outside them a browser ends the same bytes at the first `>`, so what follows is live and the filter stays. The markdown output applies no tagfilter.

Evaluation is opt-in and stays opt-in

JSX prop expressions that cannot be serialized (functions, free variables) are kept as strings by default; `evalUnserializableExpressions` runs `eval()` on them (rule: AGENTS.md, "Security"). Documentation never presents the option without the untrusted-input warning beside it.

Rules for changing any of this

The change rules are in AGENTS.md ("Security"). A trusted internal constant interpolated raw into a quoted attribute (a font stack, a class name) closes the attribute at its first quote and drops everything after it, which is why constants are escaped too.

- `scripts/html-fuzz.ts` must stay clean (how it reads each output: specs/tooling.md, "Security fuzz"). It fails on an unsafe reading of any output, and also on a live tagfilter element in the html output, on an `attributeName` targeting a URL or `on*` attribute, and on the parser's lazy line marker reaching the AST. It allows two kept shapes: a `{...}` value on a capitalized tag, except a handler unless a sink registers the tag or React holds it as a prop, and a non-object value holding a dangerous URL in a URL attribute; and a bare handler name, which holds no script, except an unprefixed one on a Solid element, which throws.
