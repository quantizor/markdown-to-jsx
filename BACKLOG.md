Open work and known issues for markdown-to-jsx. Remove an entry as the final step of the change that resolves it.

## astToMarkdown round-trip fidelity

The markdown output compiler is guarded construct by construct by the "HTML equivalence corpus" round-trip harness in lib/src/markdown.spec.ts. These cases remain:

- Two adjacent lists of the same kind re-parse as one list. The source can only separate them by a marker change (`- a` then `* b`, or `1.` then `2)`), but compileUnorderedList always writes `-` and compileOrderedList `.`, so the blank line between them joins them into one loose list. Fixing it means alternating the marker when a list follows a list of the same kind.
- A code block written through the `<pre><code>` fallback (a body compileCodeBlock judges unsafe as raw text) re-parses as a raw HTML block, not a code block: its text holds entities such as `&#42;` and a newline before `</code>`, so gfm-spec.md does not round-trip.

Add a corpus case when each is fixed.

## Known spec deviations

- Raw HTML blocks are not emitted verbatim: inter-tag whitespace and interior newlines are lost because the parser turns HTML into structured element nodes for the JSX renderers (CommonMark ex 150, 191). Semantic content is correct. Restoring verbatim bytes would require carrying a parallel source range through the AST.
- Code blocks omit the CommonMark trailing newline (`<pre><code>foo</code></pre>` vs the spec's `foo\n`). Established output shape, no rendered difference (a final empty line generates no line box).
- The html compiler writes block elements with no line break between them (`<ul><li>a</li></ul>` vs the spec's `<ul>\n<li>a</li>\n</ul>`). Established output shape, no rendered difference (whitespace between block elements draws nothing); the CommonMark conformance run's `normalizeHtml` removes it from both sides.
- Under `optimizeForStreaming`, an unclosed block-level tag on a list-marker line (`- <div>x`) is stripped as an incomplete streaming tag, leaving an empty list item until the closer arrives.
- Under `optimizeForStreaming`, an unclosed highlight (`==hi`) shows its `==` marker, while unclosed `**`, `~~`, and links hide theirs.
- A bare email whose domain label ends in `-` or `_` before a dot (`foo@a_.c`) stays text, while GFM and cmark-gfm link it: scanBareEmail applies hostname label rules (each label ends with a letter or digit, at most 63 characters). Matching GFM changes which text links, so it needs a maintainer call.

## Renderer drift

- Vue ignores an `overrides` map whose keys are all inherited (`Object.create(card)`), because it tests `Object.keys(overrides).length`, while React and the string compilers read inherited keys through `util.overrideValue`. Aligning Vue on `util.hasKeys` changes published Vue output for that shape.
- A stray `</div>` closer inside paragraph text renders as a View nested in a Text in React Native, which Android rejects; the other renderers emit it as text or drop it.
- Re-rendering a stored AST through `astToJSX` wraps a top-level inline HTML span in a `<p>` that the direct `compiler` call does not emit.
- An image whose source the sanitizer rejects (`![x](javascript:alert(1))`) renders `src=""` in the html compiler, while React omits the attribute.
- Fenced code block class names differ by renderer: the JSX renderers (react, native, solid, vue) emit `language-js lang-js` while the html string compiler emits `language-js` alone. `language-` is what hljs and prism key on and is the one to keep; `lang-` is legacy. Aligning them means either adding a duplicate class to html output or dropping `lang-` from the JSX renderers, and both change published output bytes, so it needs a maintainer call and a major or a clearly-flagged minor.
- An HTML block whose content sits on its own lines with heading syntax (`<div>\n# x\n</div>`) renders differently by renderer: the html and markdown compilers emit the block's source text, so `# x` stays literal, while the JSX renderers (react, native, solid, vue) render the parsed children, an `<h1>`. CommonMark Example 189 keeps newline-wrapped content without a blank line raw, so html is the conforming side. The block-syntax check that sends such content to block parsing feeds the JSX renderers only; aligning them changes published JSX output.
- An inline HTML element split across blocks by a block start on its second line (`<span>foo\n# bar</span>`, CommonMark gives `<p><span>foo</p><h1>bar</span></h1>`) renders differently by renderer: html emits the open and close tags where they fall, matching the reference, while the JSX renderers emit an empty element in each block (`<p><span></span>foo</p><h1>bar<span></span></h1>`). Any block start that interrupts a paragraph triggers it (`#`, `-`, `>`, and `#bar` under `enforceAtxHeadings: false`). A JSX tree cannot hold a half-open element, so the choice is which shape to emit; changing it changes published JSX output.
- A tag renamed through `overrides` (`{ Card: { component: 'aside' } }`) is renamed by the html and markdown compilers only when it is a self-closing tag standing alone as a block (`<Card />` on its own line). A paired tag (`<Card>hi</Card>`), an inline tag (`x <Card /> y`), and a tag inside a raw HTML block (`<div>\n<Card />\n</div>`) keep their written name, and a `children` attribute on the nested shape loses its text. The JSX renderers (react, native, solid, vue) rename all four. The string compilers pass raw HTML through as screened source text, so renaming there means rewriting tag names inside that text in step with the screen; changing it changes published html and markdown output.
- A raw HTML block whose screened text holds a `</pre>` but that React's Type 1 check does not read as a `<pre>` block (`<div <b c="d"/>\n<![CDATA[</pre>\n`) renders differently by renderer: Solid and Vue set the screened raw text as `innerHTML`, React drops it and renders an empty element, and html passes it through. Solid and Vue test for `</?pre` in the raw text, while React calls `parse.containsType1Tag`. Aligning them on one check changes published JSX output.
- A raw HTML block that holds a `<pre>` and closes on its first line (`<div><pre>a</pre></div>`) hands the JSX renderers a raw body that still ends in the block's own `</div>`, plus anything after it on that line (`<div><pre>a</pre></div>b`). React, Solid, and Vue put it in `innerHTML`, where a browser ignores the stray closer, but `b` lands inside the element rather than after it; React Native shows `</div>` as visible text. Reading the screened `text` alone drops `b`, so the fix splits the body at the own closer and renders what follows as siblings (the `findOwnCloseInAST` path).
- A `<pre>`, `<script>`, `<style>`, or `<textarea>` block followed by markup on the same line (`<pre>a</pre><b>x</b>`) loses that markup in the JSX renderers (react, native, solid, vue), which render `<pre>a</pre>`, while html keeps `<b>x</b>`.
- An HTML block whose opening tag holds an attribute name outside the CommonMark grammar but valid to a browser (`<div @click="x">a</div>`, `<div 0="x">`, `<div #x>`) renders as an empty element in the JSX renderers (react, native, solid, vue), while html and markdown pass the source through and a browser shows `a`. The parser keeps the whole block as `text` (`text === _rawOuter`) with no attributes or children, and `reparsedToItself`, which would return that text, runs after `stripVerbatim` has cleared `_verbatim`, so it never matches. Rendering the source as text instead changes the JSX output of the adversarial cases in the "markup a browser reads differently" tables; the faithful fix reads HTML block attributes the way a browser tokenizes them, so the JSX renderers get the element and its content.
- React's own server renderer (`react-dom/server` 19.2.8) can overflow its stack below the library's render depth limit (2,500) on a hand-built AST whose nested children are keyed arrays, so such an AST can crash React server rendering. The failing depth is not reproducible: through `astToJSX` the development build passed at 2,000, failed at 2,100, passed at 2,200 and 2,300, failed at 2,400, and passed at 2,500 and 3,000; the production build passed at 2,400 and failed at 2,500. Parser output nests far less, since the parse depth limit caps containers.
- `codeBlock` nodes carry an `infoString` field that no compiler reads and the AST type does not declare. Removing it changes the node shape callers can see, so it is a compatibility call.
- An override given as a bare tag-name string (`{ a: 'span' }`, allowed by the `Override` type through `React.ElementType`) is ignored by React and the other JSX renderers, which render `<a>`, while the html and markdown compilers rename it to `<span>`. React's `getTag` reads only a function, a `render` object, or `.component`; the string compilers use `util.getTag`, which accepts the string. Making the JSX renderers honor it changes published JSX output.
- A heading whose override props carry an `id` (`{ h1: { props: { id: 'o' } } }`) gets the slug in html output (`<h1 id="hi">`) and the override in React (`<h1 id="o">`). Either order changes one renderer's published output, so it needs a maintainer call.

## Performance

- Parse speed depends on what the process parsed before. One copy of the parser parses the stress fixture about 17% slower after parsing `gfm-spec.md` and `markdown-spec.md` than in a fresh process (six processes each way, no overlap), and compile logs tie the slow state to `parseBlocks` keeping optimized code from the earlier inputs. Unmeasured: whether real mixes of documents trigger it or only the synthetic stress fixture. A worker that cycles a corpus of real documents and compares per-document time against fresh processes settles it.
- Deeply nested containers grow quadratically with depth, bounded by the parse depth limit, because each level copies its content into a new string for the next (specs/parser.md, "Work budgets"). They parse faster than the released version (production build, best of 7, one machine: a one-line list 500 levels deep at 0.84 of its time, a one-line quote at 0.44, a multi-line list 300 levels deep at 0.08, a multi-line quote at 0.95). Passing offsets instead of copies would make them linear. scaling-smoke allows the one-line shapes a higher exponent until then; both now SKIP as too cheap at the depths the limit allows, and are judged again if they slow down.
- Input dense in `<?` processing-instruction openers parsed about 12% slower with the table-driven parser than with the parser it replaced, in one paired-gate run. Unmeasured: where the time goes; profile before changing the raw-markup scan.
- `htmlBlock` nodes take several hidden-class shapes, because `makeHtmlNode` builds a shape per optional-field mask. Measure whether one full shape with undefined fields speeds the JSX renderers' HTML paths before changing it.

## Tooling

- fuzz.spec.ts judges each adversarial shape by an absolute time budget, which a quadratic scanner passes whenever the chosen size is still cheap. Each shape it holds that scripts/scaling-smoke.ts lacks belongs there as a growth-exponent case, after which the suite deletes; a shape that tests a crash or a thrown error rather than time stays in the parser suite.
- Some Solid suite tests call the compiler without asserting anything, so they cannot fail, and several test names cite a renderer's local variables (`selfTagRegex`, `cleanedText`, `containsPreTags`, `processedChildren`) or a function the code does not have (`processNode`) instead of the behavior under test. Give each an assertion of its actual output or delete it, and rename each to the behavior it checks.
- No typecheck covers `scripts/`: verify's typecheck runs `lib/tsconfig.typecheck.json` (library and specs) and the harness workspaces, so a type error in a dev script or its spec surfaces only at run time. Add a tsconfig for `scripts/` (Bun types, the lib type roots) to verify's typecheck wave.
